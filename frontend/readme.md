# MediVault frontend

React + TypeScript frontend connected to the Express backend. The existing blue/white shell, desktop sidebar, mobile drawer, patient cards and document tables are retained. Forms and record screens use live API data rather than the original mock data. Clinical facts, IDs and audit events are never generated by the browser.

## Run locally

First configure `backend/.env` as described in [the backend guide](../backend/README.md). Atlas requires a **database user's** credentials, not the Atlas website login. Replace password placeholders and URL-encode special characters. Neither passwords nor connection strings belong in frontend environment variables.

In one terminal:

```powershell
cd backend
npm ci
# For an empty development database, create the synthetic demo account once:
npm run seed:demo
npm run dev
```

The seed command prints the demo doctor's email and a random password once. It does not reset an existing account. Use those doctor credentials on the application login screen; the Atlas database password is only for the backend connection.

In another terminal:

```powershell
cd frontend
npm ci
npm run dev
```

Open `http://localhost:3000`. Vite forwards `/api` to `http://127.0.0.1:5000`. Keep backend `CLIENT_URL=http://localhost:3000`. If changing the backend port, set `API_PROXY_TARGET` in the frontend process environment. No frontend `.env` file is necessary for this default setup.

For production, serve the frontend and `/api` under the same HTTPS origin using a reverse proxy. Vite's development proxy is not part of the static production build. Set the backend's HTTPS origin and trusted-proxy configuration accordingly. `VITE_API_BASE_URL` can override `/api`, but cookies require compatible same-site hosting.

## Included workflows

- Login, session restoration, server logout and automatic return to login on expiry.
- Paginated patient directory and server-side name/Patient ID search, including global search.
- Registration and profile editing, with blank optional fields and server-assigned Patient IDs.
- Patient cards and patient-specific document records, with no fallback to another patient's record.
- Actual multipart PDF/JPG/PNG upload, report date separate from upload time, and server-supplied file-size limit.
- PDF/image preview and original file download through authenticated API requests.
- Document category/date filters, paginated audit logs, real dashboard counts, read-only doctor settings.
- Loading, empty, validation and retry states. Failed writes are not automatically retried.

The app does not persist patient data or authentication tokens in localStorage. It removes the prototype's old `medivault_*` cache keys. Legacy fixtures under `src/mock` are unused by the live application. Insurance, national health ID and vitals remain optional API fields; the frontend displays recorded values but does not fabricate defaults.

## Checks

```powershell
npm run build
# Install Playwright's Chromium once, or use an installed Chrome browser below.
npx playwright install chromium
npm run test:e2e
```

On Windows with Chrome already installed:

```powershell
$env:PLAYWRIGHT_CHANNEL = 'chrome'
npm run test:e2e
```

Browser tests start their own backend on port 5107, frontend on port 3107 and disposable MongoDB process. They use only synthetic records and encrypted temporary local files; they never connect to your Atlas database. Tests cover desktop/mobile registration, optional-field clearing, search/pagination, patient cards, uploads, image preview, downloads, persistence after reload, audit logs, logout and session expiry. Screenshots/traces are ignored by Git.

Live Atlas and Cloudinary readiness must be verified separately. A successful local integration test does not verify credentials, cloud storage or deployment configuration.
